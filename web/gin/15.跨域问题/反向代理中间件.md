# 反向代理中间件：从「看不懂」到能改

给刚学完 gin 路由和 CORS（`Access-Control-Allow-Origin` 那套）的人。你已经会写
`c.Header("Access-Control-Allow-Origin", "*")`，但看到 `httputil.ReverseProxy` 就读不下去了。
不是代码难，而是**有两个前置概念没人讲过**：gin 的 handler 链是怎么流起来的，以及
`req.URL.Host` 和 `req.Host` 为什么是两个东西。

这一篇把这两件事讲透，再给一份能直接跑的 `main.go`（放在同目录的 `反向代理/main.go`，内容和下面完全一致）。

---

## 0. 名词先说清楚

| 名词 | 一句话解释 |
| --- | --- |
| 上游 | 反向代理把请求**转过去**的那台服务器，真正干活的那个 |
| 下游 | 浏览器 / 客户端这一端 |
| 反向代理 | 站在下游和上游中间的转发层：下游以为在跟自己说话，其实是它在帮忙转给上游 |
| Director | 你交给 `ReverseProxy` 的「改请求」回调，只收 `*http.Request`，改动直接写在参数上 |
| ModifyResponse | 「改响应」回调，上游响应回来、转发给浏览器之前调用，收 `*http.Response` |
| FlushInterval | 控制「多久往浏览器吐一次响应体」，类型 `time.Duration` |
| 预检请求 | 浏览器发正式跨域请求之前，先偷偷发的一个 `OPTIONS` 探路请求 |
| Set-Cookie | 服务器让浏览器**存** cookie 的响应头，一个响应里可以出现多条 |
| `req.URL.Host` | 拨号地址 —— 决定 TCP 连到哪台机器 |
| `req.Host` | HTTP 报文里 `Host:` 那一行 —— 上游应用层读到的那个 |

最后一行是全文重点，后面展开。

---

## 1. 读代码前必须先懂的 3 件事

### 1.1 中间件到底是个什么东西

**中间件就是一个函数**，签名 `func(c *gin.Context)`。gin 把中间件和业务 handler
**当成同一种东西**，都叫 `HandlerFunc`，装在同一条链 `HandlersChain` 里：

```text
请求进来
   ▼
[ Use 的中间件1 ] → [ Use 的中间件2 ] → [ 路由 handler ]
   先跑              再跑               最后跑
```

关键在于：**链不会自己往下走**，必须有人喊 `c.Next()`。

```go
r.Use(func(c *gin.Context) {
    fmt.Println("A 开始")
    c.Next()          // 喊这一声，链才推进到下一个 handler
    fmt.Println("A 结束")
})
r.GET("/x", func(c *gin.Context) { fmt.Println("handler 跑了") })
```

所以三件事：

- **不调 `c.Next()`** → 链停在这，后面的 handler 一个都不会跑。
- **调 `c.Abort()`** → 把 `IsAborted()` 置为 `true`，链也停住。但 gin 官方注释写得很明确：
  它**不会停止当前 handler 自己**。
- **在链尾的业务 handler 里调 `c.Abort()` 没有任何效果** —— 它的作用是掐掉「后面的 handler」，
  链尾后面本来就没 handler 可掐。

> 记住这句就够：gin 的中间件和路由 handler 是**同一个函数类型、同一条链**，区别只在先后位置。
> 想拦后续，不调 `c.Next()` 就够；`c.Abort()` 只是顺手把 `IsAborted()` 标真，好让后面判断。

### 1.2 为什么 c.Writer / c.Request 能直接喂给 ServeHTTP

代理入口长这样：

```go
proxy.ServeHTTP(c.Writer, c.Request)
```

而它的签名是：

```go
func (p *ReverseProxy) ServeHTTP(w http.ResponseWriter, req *http.Request)
```

要能传进去，`c.Writer` 必须实现 `http.ResponseWriter`，`c.Request` 必须是 `*http.Request`。
看 gin 源码（`context.go`）：

```go
type Context struct {
    Request *http.Request  // ← 就是标准库的 *http.Request，完全对得上
    Writer  ResponseWriter // ← gin 自己的接口，往下看
}
```

而 `gin.ResponseWriter`（`response_writer.go`）长这样：

```go
type ResponseWriter interface {
    http.ResponseWriter   // ← 关键：把标准库接口「内嵌」进来了
    http.Hijacker
    http.Flusher
    http.CloseNotifier
    Status() int
    Size() int
    WriteString(string) (int, error)
    Written() bool
    WriteHeaderNow()
    Pusher() http.Pusher
}
```

**Go 判断「A 能不能当 B 用」，只看 A 有没有 B 要求的全部方法。**
内嵌 = 继承它的全部方法，所以 `gin.ResponseWriter` 天然拥有 `Write` / `WriteHeader` / `Header`
三件套 —— 于是它满足 `http.ResponseWriter`，`c.Writer` 就能直接传进去。

这就是「接口签名一致」的全部含义：**不是名字一样，而是方法集覆盖了目标接口。**

### 1.3 请求完整流转

```text
┌───────────┐
│  浏览器    │   (下游)
└─────┬─────┘
      │ ① GET /proxy/api/user
      │   Host: 127.0.0.1:8080            ← 客户端自己的 Host
      │   Origin: http://127.0.0.1:5500   ← 跨域判据
      ▼
【gin 中间件层】
  ② 补 Access-Control-* 响应头
     —— 跨域响应头必须写在 body 之前；写到 body 之后再设，
        浏览器已经收到数据了，来不及。
  ③ OPTIONS 预检 → 本地回 204，不走代理
     —— ReverseProxy 完全不看 HTTP 方法，OPTIONS 会被原样转发给上游。
  ④ proxy.ServeHTTP(c.Writer, c.Request)
        outreq := req.Clone(ctx)          ← 克隆一份，客户端原件不动
      ▼
【Director：你写的那个改请求回调】
  req.URL.Scheme = "http"                 ← 改协议
  req.URL.Host   = "127.0.0.1:8081"       ← 改【拨号地址】
  req.URL.Path   = "/api/user"            ← 去掉 /proxy 前缀
  req.Host       = "127.0.0.1:8081"       ← 改【Host 头】，必须显式写
  req.Header.Set("X-Forwarded-Proto","http")
  ReverseProxy 自己加的：X-Forwarded-For = 客户端 IP   ← 默认就有，不用写
      ▼
      拨号看 req.URL.Host；报文里 Host 头看 req.Host
      ▼
【上游】http://127.0.0.1:8081/api/user
  返回 200 + body + Set-Cookie: sid=x; Domain=.example.com
      ▼
【ModifyResponse】剥掉 Set-Cookie 里的 Domain
  —— 上游下发的 Domain=.example.com 在 127.0.0.1 上无效，浏览器会直接拒收。
      ▼
⑥ 按 FlushInterval 把 body 写回浏览器，响应结束
```

**全图只有两个地方改请求，改的是两组完全不同的东西** —— 这是最容易晕的地方：

- `req.URL.Host` = 拨号地址。改它 → 决定 TCP 连到哪台机器。
- `req.Host` = HTTP `Host` 头。改它 → 决定报文里 `Host:` 那行写什么。

两者**互不默认**。`req.Host` 为空时 Transport 才会**回退**用 `req.URL.Host`；
`req.Host` 不空就用 `req.Host`，跟 `URL.Host` 毫无关系。
另外 HTTPS 下 TLS 的 SNI 取的是 `URL.Host`，所以就算 Host 头写错了，连接层照样是通的 ——
坏在应用层按 Host 做虚拟主机路由的那一步。

## 2. 完整可运行的 main.go

带一个假上游，跑这一个文件就能看完整链路。访问
`http://127.0.0.1:8080/proxy/api/user` 即可验证全部行为。

```go
package main

import (
	"io"
	"log"
	"net"
	"net/http"
	"net/http/httputil"
	"net/url"
	"strings"
	"time"

	"github.com/gin-gonic/gin"
)

// 上游地址：真正干活的那台服务器。这里用本机 8081 演示，方便单独跑这一个文件。
var upstream = "http://127.0.0.1:8081"

func main() {
	gin.SetMode(gin.ReleaseMode) // 关掉 Debug 打印，日志干净一点，便于看清自己的输出

	// 必须先解析成 *url.URL：ReverseProxy 要的是结构化的 scheme/host/path，不接受字符串。
	target, err := url.Parse(upstream)
	if err != nil {
		panic(err)
	}

	proxy := &httputil.ReverseProxy{
		// Transport：发上游请求用的「车次凭证」。
		// 不用 http.DefaultTransport 的原因：它是进程级单例，池参数改不动，
		// 而且全进程所有 HTTP 客户端共享，代理会和别的请求互相抢连接池。
		Transport: &http.Transport{
			MaxIdleConns:    100,              // 空闲连接池上限
			IdleConnTimeout: 90 * time.Second, // 空闲连接多久回收
			DialContext: (&net.Dialer{
				Timeout:   5 * time.Second, // ← 坑 不写超时，上游宕机时会一直挂着等
				KeepAlive: 30 * time.Second,
			}).DialContext,
		},

		// Director：改请求。只接收 *http.Request，改动直接写在参数上，没有返回值。
		Director: func(req *http.Request) {
			// URL 三件套：协议、拨号地址、路径。三者互相独立，都得显式改。
			req.URL.Scheme = target.Scheme
			req.URL.Host = target.Host // 拨号地址：决定 TCP 连到哪台机器
			req.Host = target.Host     // ← 坑 漏这行，上游收到的还是客户端的 Host，见坑表①
			// 去掉网关前缀，否则上游会看到 /proxy/api/user 而找不到路由。
			req.URL.Path = strings.TrimPrefix(req.URL.Path, "/proxy")
			// ← 坑 不写这行，上游分不清原请求是 http 还是 https，见坑表②。
			req.Header.Set("X-Forwarded-Proto", req.URL.Scheme)
		},

		// FlushInterval：多久往浏览器吐一次响应体。
		// 负数 = 每次写完立刻 flush（SSE / 大文件流式必须用这个）
		// 0    = 不做定期 flush
		// 正数  = 每隔这么久吐一次
		// 补充：ReverseProxy 会「自作主张」对 SSE、或 ContentLength == -1 的响应
		// 强制立即 flush，这种情况你设多少都会被忽略。
		FlushInterval: -1,

		// ModifyResponse：上游响应回来、转发给浏览器之前调用，用来改响应头。
		ModifyResponse: func(resp *http.Response) error {
			return stripCookieDomain(resp)
		},

		// ErrorHandler：上游连不上、或 ModifyResponse 返回 error 时调用。
		// 这个字段 Go 1.11 就有了，不是 1.20 的新东西，只有 1.10 及更早才会编译不过。
		// 不写它的话默认行为只是「记一条日志 + 回 502」，客户端拿到什么都不知道。
		ErrorHandler: func(w http.ResponseWriter, req *http.Request, err error) {
			log.Printf("[proxy] %s %s 失败: %v", req.Method, req.URL.Path, err)
			w.WriteHeader(http.StatusBadGateway)
			_, _ = w.Write([]byte("upstream unavailable"))
		},
	}

	r := gin.New()

	// 中间件：跨域响应头 + 预检请求本地短路。
	r.Use(func(c *gin.Context) {
		if c.GetHeader("Origin") != "" {
			// 有 Origin 说明是跨域请求。用回声而不是写死，兼容任意前端地址。
			c.Header("Access-Control-Allow-Origin", c.GetHeader("Origin"))
			c.Header("Access-Control-Allow-Methods", "GET,POST,PUT,DELETE,OPTIONS,PATCH")
			c.Header("Access-Control-Allow-Headers", "Content-Type,Authorization")
			c.Header("Access-Control-Max-Age", "600")
			// ← 坑 这些头必须写在 body 之前，所以放中间件、放 c.Next() 之前。
		}
		if c.Request.Method == http.MethodOptions {
			// ReverseProxy 完全不看 HTTP 方法，OPTIONS 会被原样转发给上游。
			// 上游通常看不懂跨域（它看不到 Origin），所以要代理层本地吃掉。
			// 如果你的上游自己已经配好 CORS，这段可以整段删掉。
			c.Abort() // ← 坑 见坑表⑤；其实不调 c.Next() 也就够了
			c.Status(http.StatusNoContent) // 预检成功回 204
			return
		}
		c.Next()
	})

	// 所有 /proxy/ 开头的请求都转发给上游。
	// 注意 *path 是 catch-all：gin 底层 radix 树不允许它和同层其他子路由共存，
	// 所以在同一组里别再注册 /proxy/get 这种路径，启动会直接 panic。
	r.Any("/proxy/*path", func(c *gin.Context) {
		proxy.ServeHTTP(c.Writer, c.Request) // c.Writer/c.Request 能直接传，见 1.2
	})

	go serveMockUpstream() // 起一个假上游，让你跑这一个文件就能测完整链路
	log.Printf("proxy :8080 -> %s", upstream)
	_ = r.Run(":8080")
}

// 剥掉 Set-Cookie 里的 Domain 属性。
// Set-Cookie 是服务器让浏览器存 cookie 的响应头，一个响应里可以出现多条。
//
// 为什么要剥：上游常下发 Domain=.example.com，浏览器访问 127.0.0.1 时
// 会因为 domain 不匹配直接拒收。剥掉后它变成绑定 127.0.0.1 的 host-only cookie，才能存进来。
func stripCookieDomain(resp *http.Response) error {
	// Header.Values 大小写不敏感，这是取「同名多条」头部的正规写法。
	vals := resp.Header.Values("Set-Cookie")
	if len(vals) == 0 {
		return nil // 上游没下 cookie，直接放行
	}

	out := make([]string, 0, len(vals))
	for _, s := range vals {
		// ← 坑 老教程里写的是 http.ReadSetCookie，Go 1.23 起改名为 ParseSetCookie，
		//    新版已删掉旧名，照抄旧博客会直接编译报错。
		c, err := http.ParseSetCookie(s) // 字符串 → 结构体
		if err != nil {
			out = append(out, s) // 解析失败原样保留，宁可不动也别误删
			continue
		}
		c.Domain = "" // 空字符串 → 序列化时不再输出 Domain 段
		c.Secure = false // 上游带 Secure 时，纯 http:// 访问同样收不到，往往要一起清
		out = append(out, c.String()) // 结构体 → 字符串
	}

	// ← 坑 必须先 Del 再逐个 Add，绝不能用 Header.Set，见坑表④。
	// 也别用 strings.Replace(s, "; Domain=...", "", 1) 这种字符串替换：
	// Set-Cookie 的值里含逗号（Expires=Mon, 02 Jan 2024 15:04:05 GMT），会切坏值。
	resp.Header.Del("Set-Cookie")
	for _, v := range out {
		resp.Header.Add("Set-Cookie", v)
	}
	return nil
}

// 假上游：故意下发带 Domain 和 Secure 的 cookie，方便你验证上面的剥离逻辑。
func serveMockUpstream() {
	mux := http.NewServeMux()
	mux.HandleFunc("/api/", func(w http.ResponseWriter, req *http.Request) {
		w.Header().Set("Content-Type", "text/plain; charset=utf-8")
		w.Header().Add("Set-Cookie", "sid=abc123; Domain=.example.com; Secure; Path=/")
		_, _ = io.WriteString(w, "from upstream, Host header = "+req.Host)
	})
	srv := &http.Server{Addr: ":8081", Handler: mux}
	_ = srv.ListenAndServe()
}
```

跑起来后你可以亲自验证三件事：`Set-Cookie` 只剩 `sid=abc123; Path=/`（Domain 和 Secure 都被剥掉）、
body 里显示的 `Host header` 是 `127.0.0.1:8081`（证明 `req.Host` 生效了）、
`OPTIONS` 请求本地回 204 而不是转发给上游。

## 3. 必须知道的 5 个坑

| # | 现象 | 原因 | 改法 |
| --- | --- | --- | --- |
| ① | 上游回 `400` / `421 Misdirected Request`，或虚拟主机路由到了错的站点 | 只改了 `req.URL.Host` 没改 `req.Host`。ReverseProxy 用 `req.Clone` 克隆请求，`Host` 头随克隆保留，上游拿到的还是客户端那个 `127.0.0.1:8080` | Director 里两行都写：`req.URL.Host = target.Host` **和** `req.Host = target.Host`。`NewSingleHostReverseProxy` 也不帮你改 —— 官方注释原话是 "does not rewrite the Host header" |
| ② | 上游判断不出请求原来是 http 还是 https，生成的绝对 URL、回调地址全是错的 | 以为 `X-Forwarded-Proto` 会自动加。ReverseProxy 默认**只**自动加 `X-Forwarded-For` | Director 里显式 `req.Header.Set("X-Forwarded-Proto", req.URL.Scheme)` |
| ③ | 改了 cookie 的 Domain / HttpOnly，浏览器收不到任何变化，白改 | 用 `resp.Cookies()` 改。它内部逐条解析 `Set-Cookie` 并**新分配** `*Cookie`，返回值跟 `resp.Header` 完全脱钩；标准库 `*Response` 也没有把 cookie 写回 Header 的方法 | 直接改 `resp.Header`：先 `Del("Set-Cookie")`，再循环 `Add("Set-Cookie", v)` |
| ④ | 上游下发了 3 个 cookie，浏览器只收到 1 个 | 用 `resp.Header.Set("Set-Cookie", ...)`。`Set-Cookie` 天然可以多条，而 `Set` 是覆盖语义，会把前面的全冲掉 | `Del` 之后用 `Add` 逐条追加 |
| ⑤ | 在业务 handler 里调 `c.Abort()`，预期拦不住的请求照样跑完了 | 以为 Abort 能「终止整个请求」。gin 的中间件和路由 handler 是同一个类型、同一条链，`Abort` 只影响**当前 handler 之后**的部分；链尾后面本来就没 handler | 想拦后续就**不调** `c.Next()`；`c.Abort()` 放在中间件里才有意义 |
