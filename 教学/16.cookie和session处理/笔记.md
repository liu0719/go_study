# 16. Cookie 和 Session 处理

## 0. 一句话建立心智模型

**Cookie 不是登录态，它只是浏览器替你自动携带的文本容器。**

```
服务端 → 响应头：Set-Cookie: sid=abc; Path=/; HttpOnly
浏览器 → 之后每次请求头：Cookie: sid=abc
```

所以"用 Cookie 做登录"的完整语义是：Cookie 里放一个**凭据**。这个凭据要么自己能被验证（无状态，JWT），要么服务端拿它去查表（有状态，Session）。本节三种方案就是这三种玩法。

---

## 1. `http.Cookie` 每个字段都是考点

```go
c.SetCookie(name, value string, maxage int, path, domain string, secure, httponly bool)
```

| 字段                   | 作用         | 踩坑点                                                   |
| -------------------- | ---------- | ----------------------------------------------------- |
| `Path`               | 只在哪些路径下回传  | `/api` 表示 `/api/xxx` 会带，但 `/` 不带                      |
| `Expires` / `MaxAge` | 过期时间       | **`MaxAge` 和 `Expires` 同时设了以 `MaxAge` 为准**            |
| `Domain`             | 哪些域名能收到    | 设 `.example.com` 子域也能拿到                               |
| `HttpOnly`           | JS 能不能读    | **true → `document.cookie` 读不到，防 XSS 偷 Cookie**       |
| `Secure`             | 是否只走 HTTPS | **设 true 后本地 `http://` 调试时浏览器根本不发这个 Cookie** ← 新手第一大坑 |
| `SameSite`           | 跨站请求带不带    | gin 的 `SetCookie` 没有这个参数，默认 `Lax`                     |

### 三个必背的安全组合

- **防 XSS 偷 Cookie** → `HttpOnly: true`
- **本地调试不生效** → 检查 `Secure`，本地必须 `false`
- **跨域请求带不上 Cookie** → 跨站场景需要 `SameSite=None` 且必须同时 `Secure=true`；另外前端 `fetch` 要显式 `{ credentials: 'include' }`，否则默认 `omit` 直接不带（这是第二大坑，比 Secure 更常遇到）

### `MaxAge` 的三种取值，语义完全不同

```go
c.SetCookie("sid", "", -1, "/", "localhost", false, true) // 立刻删除
c.SetCookie("sid", v, 0, "/", "localhost", false, true)   // 会话 Cookie，关浏览器失效
c.SetCookie("sid", v, 3600, "/", "localhost", false, true)// 持久化 1 小时
```

## 2. Session vs Token：这是本节真正的考点

|             | 方案 B：Session       | 方案 C：JWT              |
| ----------- | ------------------ | --------------------- |
| 真数据存哪       | 服务端（内存/Redis/DB）   | 客户端（Cookie 或 Header）  |
| Cookie 里放什么 | 随机 sessionId（无意义）  | 签名过的 token（含 payload） |
| 多实例部署       | **必须挂共享存储**，否则丢登录态 | 天然支持                  |
| 主动踢人下线      | ✅ 删掉服务端记录即可        | ❌ token 到期前一直有效       |
| 撤销/改权限      | ✅ 改服务端数据立即生效       | ❌ 必须重发 token 或加黑名单    |
| 跨域友好度       | 差（受 SameSite 限制）   | 好（放 Header 不受限）       |
| 典型场景        | 传统网站、管理后台、需要强制登出   | API 服务、移动端、微服务        |

**2026 年的默认选择是 JWT（或 Session + Redis）。** 只有进程内 Session + 单机，是三种里唯一"有状态但没有共享存储"的组合 —— 恰好是生产环境的错误示范，所以第 5 节专门复现它崩掉的样子。

## 3. Token 放 Cookie 还是放 Header

两条路都能走，区别在于 CSRF：

- **放 Header（`Authorization: Bearer <token>`）**：天然跨域友好，不受 SameSite 约束，且**浏览器不会自动携带**，因此不存在 CSRF 问题。JS 自己存，建议用 `sessionStorage` 而不是 `localStorage`（后者跨标签页共享，被 XSS 后长期暴露）。
- **放 Cookie**：前端省事（自动携带），但必须处理 CSRF。经典防护是 `SameSite=Lax`（现在浏览器默认值，能挡掉绝大多数跨站 POST），再加一个独立 CSRF Token 头做双重校验。

代码里 `/jwt/login` 故意把 token 同时放 Cookie 和 Header，就是为了让你能对比这两种行为。

## 4. `GET /jwt/tamper` 演示了什么

```
合法 token：  header.payload.签名    → 验签通过
篡改后：      header.改了role.admin.原签名  → 签名不匹配，拒绝
```

**结论：JWT 防篡改，不防偷看。**

- payload 只是 base64 编码，**不是加密**，任何人打开 token 就能看到里面所有内容。所以 payload 里绝不能放密码、手机号、身份证这类敏感数据，只放标识符。
- 签名靠 `hmacSHA256(payload, secret)` 算出。**secret 泄露 = 攻击者可以自己签任意身份的 token**。所以 secret 一定要放在配置/环境变量里，不要写死在代码里提交到 Git。

想真正验证"防篡改"，把 `/jwt/tamper` 返回的伪造 token 复制出来，直接请求：

```bash
curl "http://localhost:8080/jwt/me" -H "Authorization: Bearer 粘贴伪造的token"
# 返回：签名不匹配：payload 被篡改过
```

## 5. 全篇最重要：复现"Session 在多实例下丢登录态"

这是 Section 2 那张表里最要命的一行，必须亲手复现一次才记得住。

```bash
# 终端 1：起实例 A
INSTANCE_ID=A PORT=:8080 go run 16.cookie和session处理/Cookie和Session处理.go

# 终端 2：起实例 B（同一份代码，内存各自独立）
INSTANCE_ID=B PORT=:8081 go run 16.cookie和session处理/Cookie和Session处理.go
```

复现步骤：

```bash
# 1. 在 A 上登录，拿到 sessionId（-c 把 Cookie 存下来，-b 带上它）
curl -c /tmp/a.jar http://localhost:8080/session/login
# 返回 sessionId=xxx，A 的内存里现在有一条记录

# 2. 用同一个 sessionId 去问 A → 已登录
curl -b /tmp/a.jar http://localhost:8080/session/me
# 返回 userID=张三，本机在线数=1

# 3. 用同一个 sessionId 去问 B → 未登录！
curl -b /tmp/a.jar http://localhost:8081/session/me
# 返回 HTTP 401 未登录

# 4. 验证 B 的内存里确实什么都没有
curl http://localhost:8081/about
# 返回 实例ID=B，本机会话数=0（或只有它自己新建的游客 session）
```

**为什么崩：** B 的内存里从来没有过这个 `sessionId`。生产环境前面还有一层负载均衡，请求会在 A/B 之间随机分发 —— 于是用户表现为"登录了但随机掉登录态"，一个极难排查的 bug。

**怎么修（两条路）：**

1. **共享存储**：Session 数据从进程内存换成 Redis，A 和 B 读写同一份。Go 里对应 `github.com/gin-contrib/sessions` 的 `redis` store，接口和这里的 `MemorySessionStore` 完全一致（`Get/Set/Delete`），把实现换掉就行 —— 这也是为什么代码里把存储抽成接口而不是直接写死 map。
2. **改成无状态**：用 JWT。服务端不存，任何实例都能验签。

> 顺便说清楚 Go 生态的现实：标准库**没有 Session**，只有 `http.Cookie`。`golang.org/x/net/webdav/handler` 里有个 `SessionFactory` 抽象但很冷门。实际项目要么用 `github.com/gin-contrib/sessions`（官方 contrib，带 cookie/memory/redis 三种 store），要么直接用 JWT 绕开这个问题。

## 6. 面试考点清单（学完这一节你该能答的）

1. `Set-Cookie` 响应头长什么样，各属性含义是什么？
2. `HttpOnly` / `Secure` / `SameSite` 分别防什么、有什么副作用？
3. Session 数据存在哪里？多实例部署怎么保证一致？
4. Session 和 JWT 怎么选，各有什么致命缺点？
5. JWT 三段各是什么，签名防的是什么、不防的是什么？
6. JWT 放 Cookie 有什么额外风险（答：CSRF），怎么防？
7. 用户点了"退出登录"，Session 怎么做、JWT 怎么做？
   （答：Session 删服务端记录即可；JWT 需要黑名单或立刻换发新 token，否则它在过期前一直有效 —— 这正是 Session 最大的优势，别只记 JWT 的好处）
